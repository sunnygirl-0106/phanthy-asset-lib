## 0. 为什么要改（先读懂,再动手）

v1 有一个设计判断是错的：它把 admin 和主账号的待办统一收进了「审核中心」。

错在哪——这两种待办性质完全不同：

- **admin 的审核是岗位。** 他登录就是为了干这个,会主动去找入口。头像菜单对他成立。
- **主账号的审批是打断。** 他不会想着「我去审核一下」,他是在做自己事情的时候被通知到的。让他记住一个藏在头像菜单里的入口,等于让他永远想不起来。

**规则：岗位型待办放导航（我知道去哪找）,事件型待办放通知 + 现场（它来找我）。**

所以这次收敛为：

| 角色 | 入口 | 目的地 |
|---|---|---|
| admin | 头像菜单 →「审核中心」 | `#/review` 页面（作品 / 素材两个 Tab） |
| 主账号 | ① 通知铃铛 ② 团队资产库左侧边栏底部 | 团队资产库上的**抽屉** |
| 子账号 | 只有通知铃铛（看结果） | — |

**`#/review` 从此是 admin 专属地盘。**

关于「铃铛和边栏入口是不是重复」——不重复,它们各管一个时刻：铃铛负责「第一时间告诉你」,但它一被点开就标记已读、红点消失,主账号当时没空处理这条待办就从视野里蒸发了；边栏入口是**常驻兜底**,只要还有 pending 就一直挂着。

## 2. 权限层 · `src/services/permission.ts`

`canEnterReviewCenter` 收窄为 admin 专属,注释一起改写：

```ts
/**
 * 能不能进「审核中心」页面（#/review）。
 *
 * 【v2 收敛】原来主账号也能进——现在不能了。原因不是权限,是产品形态：
 * 审核中心是 admin 的岗位工作台（广场投稿、内容下架/重新上架）,他每次登录都为这个来。
 * 主账号的「资产存入申请」是被动打断,不该塞进一个他想不起来的菜单里；
 * 它改由通知铃铛推送 + 团队资产库边栏常驻入口触达,在团队库上开抽屉处理。
 */
export function canEnterReviewCenter(user: User): boolean {
  return isAdmin(user)
}
```

新增一个,给团队库和抽屉共用：

```ts
/**
 * 能不能审批「资产存入申请」——即主账号处理自己名下子账号的申请。
 * 和 canApproveDeposit（判断某一条具体申请）不同,这个只回答「这个账号有没有这项职责」,
 * 用来决定要不要渲染入口。
 */
export function canHandleDepositRequests(user: User): boolean {
  return isOwner(user)
}
```

## 3. 路由 · `src/hooks/useHashRoute.ts`

主账号的目的地是抽屉,不是页面。但抽屉状态**必须进路由**,否则通知铃铛点了没地方跳。

这也符合这个文件顶部写的设计意图（「可刷新、可后退、可分享」）。

`Route` 联合类型里 `team` 一支加一个可选段：

```ts
  /**
   * 团队资产库。drawer 段用于从别处（通知铃铛 / 边栏入口）直接唤起覆盖在页面上的抽屉——
   * 抽屉是页面的一种状态,不是另一个页面,所以做成 team 的子段而不是独立路由。
   *   #/team            纯团队库
   *   #/team/deposits   团队库 + 「资产存入申请」抽屉展开
   */
  | { name: 'team'; drawer?: 'deposits' }
```

`parseHash` 的 `case 'team'` 改成：

```ts
    case 'team':
      return { name: 'team', drawer: seg[1] === 'deposits' ? 'deposits' : undefined }
```

`routeToHash` 的 `default` 分支处理不了带参数的 team 了,单独加一支：

```ts
    case 'team':
      return route.drawer ? `#/team/${route.drawer}` : '#/team'
```

路由表注释里 `#/review` 那行改为「审核中心（**仅 admin**,头像菜单进入：作品 / 素材）」,并补上 `#/team/deposits` 一行。

## 6. 新增组件 · 资产存入申请抽屉

新建 `src/components/DepositRequestDrawer.tsx` + `DepositRequestDrawer.module.css`。

### 6.1 为什么是抽屉不是页面（写进文件头注释）

主账号只有这一种待办,撑不起一个页面——v1 里他进审核中心只看到一个 Tab 的 Tab 条,那就是个废件。更重要的是：**批准之后资产就落进背后的团队库网格里**,抽屉一关就看到东西进来了,这个闭环反馈是独立页面给不了的。

（v1 里我写过「一份审核逻辑只维护一处」——那条在这里不适用：审批逻辑本来就在 store 里,UI 外壳是廉价的；而且这个列表只有一个消费者，admin 永远看不到存入申请。）

### 6.2 形态

- 从**右侧滑出**,宽度 `420px`,高度撑满内容区,半透明遮罩盖住网格但**不要盖死**（遮罩透明度低一点,让人看得见背后的团队库）。
- 点遮罩 / 按 `Esc` / 点关闭按钮 → 关闭,并 `navigate('#/team')`（把 `drawer` 段从路由里去掉）。
- 头部：标题「团队资产存入申请」+ 一句副标题「子账号把项目里的资产存进团队库,需要你点头」+ 关闭按钮。
- 主体：**待处理**分组在上（有操作按钮）,**已处理**分组在下（折叠,默认收起,只显示条数）。
- 每一行：缩略图（用 `application.assetId` 去 `world.assets` 反查封面,查不到给占位图,**不要崩**）+ 资产名 + 「申请人 · 来自某项目」+ `通过` / `驳回` 两个按钮。
- 驳回复用现有的 `ReviewReasonModal`,`presets` 传 `DEPOSIT_REJECT_REASONS`。
- 空态：「暂无待处理的申请。」——但正常情况下入口在 count=0 时就不渲染,用户走不到这个空态；它只是抽屉打开后最后一条被处理完的兜底。

### 6.3 数据

直接复用 v1 里已经写好的 `selectDepositRows(state)`,**不要再造一份派生逻辑**。如果它现在挂在 `ReviewCenterPage` 里,把它留在 `useStore.ts`（v1 规划本来就要求放那儿）。

## 7. 团队资产库 · `src/pages/TeamLibraryPage.tsx`

### 7.1 入口从工具条移到左侧边栏底部

**删掉** `toolbarLeft` 里现在那个 `pendingEntry` 按钮,`toolbarLeft` 恢复成空 `<div />`。

**改到左侧边栏底部**。`.sidebar` 已经是 `display:flex; flex-direction:column`,所以入口块加 `margin-top: auto` 就能自动贴底,不用改容器。

结构：

```tsx
<aside className={styles.sidebar}>
  {CATEGORIES.map(...)}

  {/* 存入申请入口：只在主账号且确有待办时出现（§7.2）。 */}
  {canHandleDepositRequests(user) && pendingDeposits > 0 && (
    <button
      className={styles.depositEntry}
      onClick={() => navigate({ name: 'team', drawer: 'deposits' })}
    >
      <img className={styles.navIcon} src={assetUrl('assets/icons/clock.svg')} alt="" aria-hidden />
      <span className={styles.depositLabel}>资产存入申请</span>
      <span className={styles.depositCount}>{pendingDeposits}</span>
    </button>
  )}
</aside>
```

样式要点（`TeamLibraryPage.module.css`）：

- `.depositEntry { margin-top: auto; }` —— 贴底的关键。
- 上方加一条 `border-top: 1px solid var(--line-soft)` 作分隔,并留 `padding-top`。**这条分隔线很重要**：它让这个入口读起来是「另一类东西」,而不是第六个类目。
- 内边距、字号、图标尺寸对齐现有的 `.navItem`,保持边栏节奏一致。
- 颜色用 `var(--accent)` 系,但**不要做成实心主按钮**——它是提示,不是页面主动作。可以直接复用现有 `.pendingEntry` / `.pendingCount` 的配色,只改布局（把 `.pendingEntry` 重命名为 `.depositEntry`,别留两套）。
- 底部留 `margin-bottom: 16px`,别贴死屏幕边缘。

### 7.2 ★ 硬要求：count 为 0 时整个入口不渲染

常年挂一个「资产存入申请 0」会训练人忽略它,那比没有更糟。**不要**改成灰态或 disabled,直接不渲染。

### 7.3 挂抽屉

```tsx
const { route, navigate } = useHashRoute()
const drawerOpen = route.name === 'team' && route.drawer === 'deposits'
...
{drawerOpen && canHandleDepositRequests(user) && (
  <DepositRequestDrawer onClose={() => navigate({ name: 'team' })} />
)}
```

注意那个 `canHandleDepositRequests` 守卫：子账号手敲 `#/team/deposits` 不能开出抽屉。

`useStore.ts` 里两条发给主账号的通知,`link` 都要改（v1 里指向 `#/review`,主账号现在进不去了）：
