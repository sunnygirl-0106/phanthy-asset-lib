## 〇、这次到底在改什么（一句话）

**把资产详情页中栏从「定稿大图」改成「预览台」，把生成结果从「暂存区 → 人工保留」改成「直入候选池」，并在中间新增一个「待定稿」状态。**

改之前的流程：

```
点生成 → 4 张进"本次生成"暂存区 → 用户勾选 → 点「保留选中」→ 进候选池 + 第一张自动定稿
                                              ↘ 点「都不要」→ 全丢
```

改之后的流程：

```
点生成 → 4 张直接进候选池（右栏）→ 中栏自动预览第一张 → 用户逐张预览 → 点「设为定稿」→ 成品
```

**为什么改**：「保留选中 / 都不要」是一道用户不理解、也不需要做的选择题。图生成出来了就是生成出来了，星钻已经扣了，让用户在"入库"和"丢弃"之间做一次决策，等于把系统的存储问题包装成用户的决策负担。真正需要用户决策的只有一件事——**哪张是定稿**。

**顺带解决的问题**：项目库工具栏那个「批量生成」在旧模型下是走不通的——批量生成 10 个空壳会留下 10 个待处理暂存区，用户得逐个进详情页点「保留选中」。改完之后批量生成才真正成立。

### 1.4 `removeCandidate` 补全状态跃迁

**文件**：`src/services/assetService.ts` 第 86–96 行

改前（**现存缺陷**：删光后 `cover` 置空了，但 `status` 还留在 `'done'`，靠详情页的确认弹窗在外面补救）：

```ts
export function removeCandidate(source: Asset, candidateId: string): Asset {
  const removed = source.candidates?.find((c) => c.id === candidateId)
  if (!removed) throw new AssetRuleError('候选图不存在')
  const rest = (source.candidates ?? []).filter((c) => c.id !== candidateId)
  const removedWasFinal = removed.url === source.cover
  return {

    candidates: rest.length ? rest : undefined,

```

改后（状态跃迁收进服务层，UI 不再负责补救）：

```ts
/**
 * 从候选池删一张（不可变）。0807：把状态跃迁一并收进来。
 *   · 删的不是定稿 → 池少一张，status / cover 不动。
 *   · 删的是定稿、池里还有别的 → 顶第一张上来当新定稿，仍是 done（规则 18：定稿只能换不能删）。
 *   · 删掉最后一张 → 池空、cover 空、status → 'empty'（降级成空壳，提示词等一概保留）。
 */
export function removeCandidate(source: Asset, candidateId: string): Asset {
  const removed = source.candidates?.find((c) => c.id === candidateId)
  if (!removed) throw new AssetRuleError('候选图不存在')
  const rest = (source.candidates ?? []).filter((c) => c.id !== candidateId)
  if (rest.length === 0) {
    return { ...source, candidates: undefined, cover: '', status: 'empty' }
  }
  const removedWasFinal = !!source.cover && removed.url === source.cover
  return {
    ...source,
    candidates: rest,
    cover: removedWasFinal ? rest[0].url : source.cover,
  }
}
```

> 注意 `removedWasFinal` 前面加了 `!!source.cover &&`：待定稿态 `cover === ''`，不加这个判断，`removed.url === ''` 恒为 false 其实也没事，但显式写出来意图更清楚。

**验收断言**：项目库某资产有 3 张候选、第 2 张是定稿。删第 2 张 → 第 1 张变定稿，卡片封面跟着换。再删到只剩 1 张、再删 → 资产降级成空壳，卡片显示「待生成」，提示词还在。

```ts
/** 生成：先进「生成中」骨架态，1.2s 后把 genCount 张直接并入候选池，并自动预览第一张。 */
function doGenerate() {
  if (!canRegen || generating !== null) return
  if (!promptDraft.trim()) {
    setResult({ ok: false, message: '先写提示词再生成' })
    return
  }
  if (promptDraft !== (asset!.prompt ?? '')) setPrompt(asset!.id, promptDraft)
  setGenerating(genCount)
  const src = genSourceOf(asset!)
  const urls = Array.from({ length: genCount }, (_, i) => `${src}?g=${Date.now()}${i}`)
  window.setTimeout(() => {
    const r = appendCandidates(asset!.id, urls)
    setGenerating(null)
    setResult(r.ok ? { ok: true, message: `${r.message} · 消耗 ${genCount * COST_PER_IMAGE} 星钻` } : r)
    // 生成完自动预览本批第一张——否则用户点了生成，中栏还停在旧定稿上，像什么都没发生。
    // 已有定稿的资产同样要跳过去看新图（用户刚花了星钻，第一诉求就是看结果）。
    if (r.ok) {
      const fresh = useStore.getState().world.assets.find((a) => a.id === asset!.id)
      const firstNew = fresh?.candidates?.[(fresh.candidates?.length ?? 0) - urls.length]
      if (firstNew) setCenterKeptId(firstNew.id)
    }
  }, 1200)
}
```

> **`?g=` 后缀说明**：候选按 url 认定稿（`?g=N` 是权宜之计，见交接文档六节 b）。这里改用 `Date.now()+i` 而不是全局自增，是为了多次生成之间也不会撞号。**保留这个后缀，不要"顺手优化掉"。**

## 八、规则改写（同步进 PRD 附录）

**规则 18 改写**（原文："定稿只能被「换」，不能被「删」。定稿大图位置不提供删除入口。"）:

> **18（0807 改写）. 删除的对象永远是候选池里的某一张图，不是"定稿"这个身份。**
> 预览台和右栏两处都可以删。删到的恰好是当前定稿，就从池里顶一张上来当新定稿；删掉最后一张，资产降级成空壳（提示词/参考图/音色全留）。想整份重来走头部「删除资产」。

> 改写理由：中栏不再是"定稿位"，它是预览台——预览的是池里任意一张，删它就是删一张候选，跟"删定稿"不是一回事。原规则的保护意图（不能一手滑把成品变空壳）由服务层的状态跃迁 + 最后一张的确认弹窗承担，不需要靠"藏起删除按钮"来实现。

**规则 19 补充**：

> 19（补充）. 库的网格只展示定稿。**待定稿资产还没有定稿，拿候选池第一张顶上并打「待定稿」角标**——依旧不叠卡边、不打候选数角标。

**新增规则 21**：

> 21. **生成结果直入候选池，不设人工"保留/丢弃"关卡。** 星钻在生成那一刻就扣了，图生成出来就归这份资产所有。用户唯一需要做的决策是**哪张当定稿**。不满意的图逐张删。

**新增规则 22**：

> 22. **「上传本地图片」和「添加参考图」是两个入口、两件事。** 前者=这张图就是资产图，直入候选池；后者=照着这个画，进 `referenceImages`。任何一处入口不许合并。
